# Save a fresh Session Prep Chat answer

## Outcome and scope

A completed factual answer in the default Chat format currently gains its
Markdown save action only after a full reload restores it from governed history.
Expose `Save answer .md` immediately on a fresh standard response. Use the
existing exact-answer Blob download and its current record-generation guards.
Document responses keep their existing `Download .md` action. Saved answer
bytes, metadata and generic filename remain unchanged.

This is Tier 2 because the panel can display provider-owned chart content. The
change adds no record authority, storage, source access or external transmission.
Emergency and sensitive-disclosure responses receive no new action; explicit
`feature_actions` suppression continues to hide it. The same generation,
record-ready and client-ID checks deny retained callbacks after a record change,
revocation, failed bootstrap or panel destruction.

## Release sequence

1. Independently review the exact final Sovereign source after publication and
   satisfy the existing repository checks and approval settings.
2. Add Core's new vendored panel bytes, content digest, SRI and immutable upstream
   source reference in a separately reviewed asset-pin change, retaining the
   former immutable asset for already-open clients. Core loads that
   pinned local asset; a Sovereign image update alone cannot expose the action.
3. Build and verify the paired merged Core/provider Sovereign artifacts through
   their reviewed staging release paths. Preserve existing Scribe services and
   configuration. No feature cohort, service switch or production activation is
   part of this source change.

The existing provider Session Prep release controls bound availability. The
founder owns the coordinated staging release and its first provider-own-visit
synthetic acceptance. Source publication is not a deployment or activation.
Sovereign owns no schema, and this change introduces no data or migration rung.

## Validation and acceptance

The existing actual-panel history/export harness must exercise one fresh factual
Chat turn without history hydration and verify that saving creates exactly one
Markdown Blob containing the canonical UTF-8 answer, with no network/model
request. It also verifies unchanged Document download, standard suppression,
emergency/sensitive-disclosure exclusion, record-switch/destroy callback denial,
and the existing history, revocation, bootstrap and recovery protections.

After the paired staging release, use a known fictional provider-owned visit.
Ask one factual chart question in Chat, save its completed answer before any
reload, and compare the downloaded bytes and dated source cutoff with the
rendered answer. Reopen the visit and verify its saved conversation still has
the existing history save action. A foreign-owned visit must expose no panel or
export control. Record exact deployed image/asset identities with these outcomes.

## Recovery

Before deployment, revert this source commit normally. After release, restore
the retained migration-compatible Core artifact and its former panel pin as a
reviewed recovery operation, keeping the corresponding accepted provider
contract. This restores the prior history-only Chat save behavior; it deletes
no saved conversation, chart data or downloaded file. Preserve the existing
Document export and all record/presentation restrictions during recovery.

Generic filenames, absent visit/question export headers, and old-conversation
layout are separate follow-ups. They are not changed or claimed resolved here.
